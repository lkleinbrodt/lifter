# CLAUDE.md - Lifter Codebase Guide

## Project Overview

Lifter is a React Native/Expo mobile fitness app that supports two lifting programs, each on its own "side" of the app:

- **5/3/1** (modified): calculates training weights from training maxes and tracks workout completion.
- **GSLP** (Greyskull LP): alternating A/B sessions with per-lift linear progression driven by logged AMRAP reps.

The app opens to a program picker (`app/index.tsx`) and reopens straight into the last-chosen program. On GSLP, the Settings tab has a Program row that returns to the picker; 5/3/1 keeps its header chip. Both programs share the accessory exercise library. The app runs on iOS, Android, and Web.

**Stack**: Expo SDK 54, React 19, React Native 0.81, TypeScript 5.9, Expo Router 6

This is a **personal, single-user app** for the developer's own iPhone. It is not distributed via the App Store or TestFlight, and there is no plan to ever do so — don't suggest `eas submit` or App Store Connect workflows.

### Design principle: built for one user who owns the code

Landon is the only user, he knows how the app works, and he can change the source whenever he wants. Design for that:
- Anything that can live in code stays in code: program templates, the exercise catalog, rest defaults, set prescriptions. Don't build settings screens, template editors, or "create your own X" flows for things he'd just edit in the repo.
- In-app UI is for what changes *during a workout* (logging sets, swapping an exercise for today, the rest timer).
- Skip onboarding, explanatory copy, empty-state polish and other "general audience" affordances.
- Keep it extensible but lean. Programs differ (GSLP progresses off the AMRAP set; 5/3/1+ will differ), so each program plugs in its own rules. Don't generalize further until a second program actually needs it.

**Lifter 2.0** (turning Lifter into the in-workout tracker that replaces the Strong app) is planned in `docs/lifter-2-plan.md`. Read it before working on workout tracking, the log, or the Strong import.

## Deployment & Distribution

Full walkthrough in `MOBILE.md`. Same workflow as the `artoo` app in `~/Projects/landonkleinbrodt`.

- **Installing on the phone**: `npm run release:ios` on the Mac, phone connected over USB (or paired Wi-Fi). Runs `npx expo run:ios --device --configuration Release` — a local Xcode Release build with the JS bundle embedded, signed with the developer's personal team. No EAS Build, TestFlight, or App Store Connect.
- **OTA updates** (JS/asset-only changes, the common case): `npm run update:ota -- "what changed"`. Publishes to the `preview` channel, which the build is pinned to via `updates.requestHeaders["expo-channel-name"]` in `app.json`. This works from any machine that has `eas-cli` logged in as `lkleinbrodt`, including `chewy`. The script refuses to run unless on a clean `main` (the update bundles the working tree; override with `OTA_ANY_BRANCH=1`).
- **When a new build (not just an OTA update) is required**: native code changes, a new native module/config plugin, icon/splash changes, or a bump to `version` in `app.json`. `runtimeVersion` policy is `appVersion`, so a bumped version needs a matching new build before OTA updates for that version apply. After native config changes, use `npm run release:ios:full` so `ios/` gets regenerated. `ios/` is gitignored and generated by `expo prebuild`.
- `ios.appleTeamId: "DU26G2LJFP"` in `app.json` (the developer's individual Apple Developer team) is written into the Xcode project at prebuild. That skips the Xcode signing setup and avoids the unrelated "De la Cruz Consulting LLC" org team. Don't put `appleTeamId` in `eas.json`: it isn't a valid key there, and eas-cli rejects the whole file.
- `eas.json` has only a `preview` build profile (cloud, ad-hoc), a fallback if the Mac isn't available; it builds onto the same `preview` channel. There is no `production` channel or profile, so never push updates to one.
- On the phone, Settings (gear icon) → "Check for update" downloads the latest OTA and restarts, instead of relaunching twice.
- `scripts/patch-prompts-confirm.sh` (postinstall) patches a `prompts` crash that happens when the phone is locked during install.
- `plugins/without-push-entitlement.js` strips the push entitlement that `expo-notifications` adds. The personal team can't sign push, and Lifter only uses local notifications. It must stay listed before `expo-notifications` in `app.json`.
- If a Release build fails in "[RNDeps] Replace React Native Core" with `ENOTEMPTY`, something (Finder/Spotlight `.DS_Store`) is writing into `ios/Pods/React-Core-prebuilt` mid-delete. Do the swap by hand, then rebuild:
  1. `rm -rf ios/Pods/React-Core-prebuilt && mkdir ios/Pods/React-Core-prebuilt`
  2. `tar -xf ios/Pods/ReactNativeCore-artifacts/reactnative-core-<rn>-release.tar.gz -C ios/Pods/React-Core-prebuilt`
  3. `printf Release > ios/Pods/React-Core-prebuilt/.last_build_configuration`
- Building with `-destination 'generic/platform=iOS'` avoids needing the phone unlocked during the build. Then install with `xcrun devicectl device install app`.
- Header buttons on iOS 26: render plain text in `headerRight` (no background). iOS wraps header items in its own glass capsule, so a filled pill shows a double ring. `unstable_headerRightItems` (native bar items) silently broke navigation to the screen on this build; don't use it.

## Architecture & Key Patterns

### Routing
Expo Router with file-based routing. Each program lives under its own directory (`app/531/`, `app/gslp/`) with a Stack layout wrapping a `(tabs)` group, so detail screens push over the tab bar. Both tab layouts render `components/program-tabs.tsx`. Dynamic routes use `[slug]` and `[name]` parameters.

### State Management
- **Local state**: `useState()` for UI state
- **Persistent storage**: AsyncStorage via `lib/storage.ts` (no backend/database)
- **Focus-based reload**: `useFocusEffect()` to refresh data when navigating between screens

### Data Model
Shared AsyncStorage keys:
- `@active_program` — `'531' | 'gslp'`, the program the app reopens to

5/3/1 keys:
- `@user_maxes` — `{ squat: number, bench: number, deadlift: number, weightedPullupWeight: number }`
- `@completed_workouts` — `string[]` of workout IDs like `"1-squat"`, `"3-deadlift"`

### 5/3/1 Program Logic (`lib/workout-plan.ts`)
- **Training Max** = 1RM x 0.90
- **Set weights** = Training Max x percentage, rounded to nearest 5 lbs
- **4 weeks**: Week 1 (5/5/5+), Week 2 (3/3/3+), Week 3 (5/3/1+), Week 4 (Deload)
- **4 workout days**: Squat, Bench, Deadlift, Weighted Pull-Ups
- **Plate math**: Calculates plates per side from total weight (bar = 45 lbs)
- Workout IDs follow the pattern `{week}-{day}` (e.g. `"2-bench"`, `"1-weighted-pullups"`); detail route is `/531/workout/{id}`

GSLP keys:
- `@gslp_state` — `{ weights: Record<GslpLiftKey, number>, pullVariant: 'latPulldown' | 'chinup', accessoryPicks: Partial<Record<AccessoryArchetype, string>>, history: GslpSessionLog[] }`
- The in-progress workout lives in SQLite (the one `workouts` row with no `finished_at`), saved on every edit.
- `@rest_timer` — the running rest timer (`endsAt`, `durationSec`), so it survives a relaunch
- `@rest_voice` — `'jarvis' | 'elle'`, which voice says "Rest is over" (Settings → Rest voice)

### GSLP Program Logic (`lib/gslp.ts`)
- **Rotation**: strict A/B alternation (A/B/A, then B/A/B). The next workout is the opposite of the last logged one. Week/day come from the session index (3 per week).
- **Workout A (vertical)**: OHP, pull (lat pulldown 2×8, 1×8+ or chin-up 2×5, 1×5+), squat. **Workout B (horizontal)**: bench, row, deadlift (single 1×5+).
- **Warmups**: 55%×4, 70%×3, 85%×2 of work weight, rounded to 5, never below the bar.
- **Progression** (per lift, from AMRAP reps): hit target = +2.5 upper / +5 lower; 10+ reps = double jump; below target = −10% (rounded to the lift's jump, floored at its minimum, e.g. 95 for deadlift).
- Finishing a session writes a history entry with before/after weights; **Undo** on the latest entry restores the before weights.
- **Accessories** are push / pull / core slots (plus an optional hamstring slot on A), each taking the opposite orientation from the day's main lifts: A = horizontal push, horizontal pull, anti-extension core, [hamstring]; B = vertical push, vertical pull, anti-rotation core. Each archetype has an exercise pool in `accessoryArchetypes` (with equipment); only the archetype is fixed, and the last pick per archetype is saved as `accessoryPicks` in `@gslp_state`. Prescription: 2–3 × 10–15 (30–45s for timed), hamstrings 2 × 10.
- The app deliberately has no injury/pain copy or pain-stop logic; the user manages that themselves.

### Key Types (`lib/storage.ts`, `lib/workout-plan.ts`)
```typescript
type LiftKey = 'squat' | 'bench' | 'deadlift';
type Maxes = Record<LiftKey, number> & { weightedPullupWeight: number };
type WorkoutDayKey = LiftKey | 'weighted-pullups';
type WorkoutSet = { percent: number; reps: string; amrap?: boolean };
```

## Conventions

### TypeScript
- **Strict mode** enabled (`tsconfig.json` extends `expo/tsconfig.base`)
- Path alias: `@/*` maps to project root (e.g. `@/lib/storage`, `@/constants/theme`)

### Styling
- React Native `StyleSheet.create()` — no CSS-in-JS libraries
- Tokens in `constants/theme.ts` (spec: `docs/ui-overhaul-proposal.md`): colors `C.*`, `Type.*`, `Space`, `Radius`, `Shadows.float`. `Colors.dark.*` remain as aliases for older screens.
- Text is SF Pro, numbers are Menlo with tabular figures (`ThemedText num` / `numStyle`). `USE_MENLO_TEXT` flips all text to Menlo.
- Dark-only: `Appearance.setColorScheme('dark')` at startup so system alerts match.
- Cards are flat (no shadows); only floating things (minibar, menus, sheets) use `Shadows.float`.
- No svg in the build: charts, sparklines, the rest ring and the plate diagram are drawn with Views.

### Components
- Function components with hooks (no class components)
- PascalCase for components, camelCase for functions/variables
- kebab-case for filenames (e.g. `themed-text.tsx`, `workout-plan.ts`)
- UI primitives in `components/ui/`, screen-level composition in `app/`
- Haptic feedback via `expo-haptics` on interactive elements

### Linting
- ESLint with `eslint-config-expo/flat` (flat config format)
- Config in `eslint.config.js`, ignores `dist/*`
- Run with `npm run lint`
